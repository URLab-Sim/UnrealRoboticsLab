# Regenerating the Profile

The MuJoCo element components under `Source/URLab/*/MuJoCo/Gen/` are
generated from MuJoCo's own MJCF schema and checked in. Read this before
editing anything in or near that tree. For what the pipeline is and why,
see [Generation](../concepts/generation.md).

## Where everything lives

| Path | What |
|---|---|
| `third_party/MuJoCo/src/src/xml/mjcf.schema` | upstream's grammar, the source of truth |
| `protospec/protospec_gen/frontend.py` | reads the schema with MuJoCo's own parser, applies the overlay, builds the AST |
| `protospec/protospec_gen/overlay.py` | the grammar half of the hand-maintained tables |
| `protospec/protospec_gen/overlay_ue.py` | the Unreal half |
| `protospec/protospec_gen/emit.py` | emits ProtoSpec's own object model into `protospec/lib/generated/` |
| `protospec/protospec_gen/emit_ue.py` | emits URLab's profile into `Source/URLab/*/MuJoCo/Gen/` |
| `Source/URLab/Public/MuJoCo/Spec/MjGenHooks.h` | the ten-entry-point seam hand code goes through |
| `Source/URLab/Private/MuJoCo/Spec/MjSpecWriteHooks.cpp` | the writes the generator cannot express |

The MuJoCo submodule also contains a directory called `protospec/`. It is
not consumed. The live tree is the one at the plugin root.

## Running it

Python tooling uses [uv](https://docs.astral.sh/uv/), and every ProtoSpec
command runs from the `protospec/` directory:

```bash
cd protospec
uv run pytest                                  # schema, generator, extractors
uv run python -m protospec_gen.emit --check    # ProtoSpec's own generated code
```

The Unreal profile is regenerated from the plugin root, by a wrapper that
finds the generator for you:

```powershell
.\Scripts\regen_ue_profile.ps1            # rewrite Source/URLab/*/MuJoCo/Gen
.\Scripts\regen_ue_profile.ps1 -Check     # fail if it is out of date
```

```bash
./Scripts/regen_ue_profile.sh
./Scripts/regen_ue_profile.sh --check
```

`-Check` regenerates in memory and compares byte for byte. It writes
nothing, so it is safe to run at any time.

The generator reads the schema from the submodule working tree, so the
submodule has to be at the version you want before you regenerate.

## The build gate

`Scripts/build_and_test.ps1` runs the check before invoking UBT and
prints:

```
>>> Profile drift gate: regen_ue_profile.ps1 -Check
```

Exit code 4 is drift. Re-run the generator without `-Check`, commit the
output, and run the script again.

**Confirm you saw that line.** If `uv` is off PATH or the generator is
missing, the script prints a `WARNING:` naming what it could not find and
continues *without* gating. A skipped gate and a passing gate have the
same exit code.

## Never edit the Gen tree

Every file under `MuJoCo/Gen/` carries this banner:

```cpp
// Generated by protospec_gen.emit_ue -- do not edit.
```

There are no marker-fenced regions, so there is nowhere in those files
that hand edits survive. The next regen replaces the whole file.

Where a change belongs instead:

| You want to change | Edit |
|---|---|
| which reflected type a spatial attribute stores in | `overlay_ue.UE_KIND` |
| which folder an element header lands in | `overlay_ue.UE_FAMILY_OF_ELEMENT` / `UE_FAMILY_OF_SECTION` |
| which properties sit behind Advanced | `overlay_ue.UE_ADVANCED` |
| which `mjs_*` call creates an element | `overlay_ue.SPEC_CREATE` |
| which struct an embedded element writes onto | `overlay_ue.SPEC_TARGET` |
| a write the generated path cannot express | `overlay_ue.SPEC_WRITE_HANDLERS` plus a hook in `MjSpecWriteHooks.cpp` |
| what an MJCF attribute *means* | `overlay.py` |
| per-instance Unreal state on an element | a hand subclass of `UMj<El>Base`, registered with `MjSetElementClass` |

An overlay entry naming something the schema does not declare fails
generation by name, so a stale row cannot sit there unnoticed.

## Answering a gate

Gate failures name the exact table row to edit. Two rules apply to all of
them.

**Edit the table, never the gate.** Loosening a gate to get a green run
removes the only thing that would have caught the next occurrence.

**Refresh baselines last.** Two gates compare against a recorded
baseline: `classified_attrs.json` for the angle and reference heuristics,
`doc_anchors.json` for the manual anchors. Both are regenerated:

```bash
cd protospec
uv run python -m protospec_gen.frontend --update-baseline
uv run python -m protospec_gen.xmlref --update-baseline
```

Refresh them *after* answering the gates. The baseline is what makes
"new" mean anything, and refreshing first is how an unclassified
attribute becomes permanently invisible.

## Write hooks carry citations

`MjSpecWriteHooks.cpp` reproduces rules from MuJoCo's own MJCF reader for
attributes the reader interprets rather than stores, and cites the
upstream file and line each one mirrors. Two obligations follow:

- If you change a hook, re-read the upstream location and update the
  citation. The citation is part of the code.
- Nothing checks that a citation still describes the code it names, so
  re-reading them is a manual step of every MuJoCo bump.

A hook that gets a rule wrong produces a model that compiles. The live
compile-parity check is what catches it, not the compiler.

The hook registry is checked against the generated table at startup, so a
hook the generator expects and the registry does not have is an error
rather than a missing write.

## The generated layer can be absent

ProtoSpec is staged into `third_party/install/protospec/` by
`protospec/build.ps1` or `build.sh`, which is deliberately **not** a step
of `third_party/build_all`. When the staging is missing,
`URLab.Build.cs` defines `URLAB_PROTOSPEC=0`, `URLAB_MJ_GEN` follows it
to 0, and everything depending on generated types compiles out. The build
succeeds and the automation suite's generated tests go with it.

So a green build is not evidence the profile is there. Check for the
directory and for the absence of this line:

```
URLab: ProtoSpec is not installed under third_party/install/protospec -
building without the generated MuJoCo spec profile.
```
